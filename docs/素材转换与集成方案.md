# deskpet 素材转换与集成方案

> 状态：**已决策 + 已集成**。记录「AI 生成视频（mp4）→ 桌宠可用透明 webm」的转换管线、
> 跨动画共享归一化基准，以及集成到程序内的最终决策。
> 配套：[需求规格](需求规格.md)、[可行性分析与技术选型](可行性分析与技术选型.md)。
> 当前实现：转换管线抽为 `src/convert.rs`（`convert_file()` 函数，**程序内置能力**，供异步转换作业调用）；
> `src/bin/convert_asset.rs` 为开发期 CLI 包装（验证用，主程序不依赖）。
> **本迭代决策**：转换引擎调用**系统 ffmpeg / ffprobe 二进制**（解码/编码/alpha-mux），Rust 负责
> HSV 抠像 / despill / 水印 / 归一化；「内嵌 libav\* 静态库」仍为 §4 的**后续方向**（见 §6.5）。

---

## 1. 背景与目标

- 素材来源：AI 生成的**绿幕视频**（如豆包生成的透明角色动画），为 mp4，**无 alpha 通道**。
- 目标：把这类 mp4 转成项目可直接解码播放的 **VP9 + alpha WebM**（alpha 存于 Matroska
  `BlockAdditional`，见 `src/webm.rs`；发布物仅二进制，素材外置）。
- 关注点：抠像质量、跨动画体形一致、不显著增大分发包、Windows/macOS 双平台。

---

## 2. 转换管线（现实现，`src/bin/convert_asset.rs`）

```
绿幕 mp4
  → HSV 色相绿幕抠像   （仅"绿相 70~170° 且 饱和/明度≥0.15"判为背景；色相边界 6° 渐变；非绿色不误抠）
  → despill 去绿边     （前景/边缘绿色过量压回 max(R,B)）
  → 水印处理           （四角边距整块置透明；Doubao 水印常落四角；允许裁掉少量内容）
  → 归一化到 640×360   （裁剪到角色 → 等比缩放 → 居中、脚底对齐）
  → 编码 VP9-alpha-webm （`-c:v libvpx-vp9`；alpha 写 BlockAdditional）
```

- 画布固定 **640×360**：项目窗口按 `CANVAS_W×CANVAS_H=640×360`、`PAD=30` 分配 `render_buf`
  （`src/state.rs`/`src/pet.rs`），只认宽度=640 的素材，否则会被截断（实测 1280×720 只显示头部）。
- 现运行依赖：ffmpeg/ffprobe（解码 mp4、crop/scale/pad、编码 webm）；libvpx 由项目静态链接。

---

## 3. 跨动画共享归一化基准（设计要点）

- 问题：同一只宠的多段动画若各自独立归一化，**体形大小**会不一致（把"姿态高度"误当"角色大小"）。
- 思路：统一的是**角色体形比例**，不是每帧包围盒。做法（锚点法）：
  1. 选定基准动画 `ref`（推荐：idle 待机/站立）。
  2. 在其静止帧（首尾几帧）测角色站立高度 `H_ref`。
  3. 计算全局共享缩放 `s = TARGET_H / H_ref`（所有动画共用）。
  4. **所有动画都乘同一个 `s`**（不各自重算）→ 体形严格一致。
  5. 每段独立定位：水平按"非透明像素 x 中位数"居中；垂直按"最低 alpha 像素"对齐画布底线。
  6. 统一落到 **640×360** 画布。
- 实现形态：工具需变为**按宠物（批量）模式**，知道哪些动画属于同一只宠并一起处理：

  ```
  convert_assets <目录> [--idle 待机名] [--target-h 295] [--canvas 640x360]
  ```

## 4. 集成到程序内的最终决策

- **方向**：把转换作为程序**内置能力**（控制台内让用户上传 mp4 → 自动出可用 webm），不做单独 CLI。
- **采用方案**：**统一链接 ffmpeg（libav\* 静态库）**，macOS 与 Windows 一致。
- **体积**：可接受 **约 20~30 MB** 的体积增长。
- **链路**：用 libav\* 做「mp4 解封装 + H.264 解码 + VP9-alpha 编码 + WebM alpha 封装 + scale」，
  我们保留 **Rust 实现**的「HSV 抠像 / despill / 水印 / 归一化」。
- **集成时机**：现阶段转换仍是独立工具；**后续**接入程序内，成为上文 §6.2 的**异步转换作业**
  （上传 mp4 → 转换 → 注册为宠物动作）。
- **许可**：libav\* 为 LGPL；项目为 MIT 且源码公开，需附 LGPL 许可文本并满足重链接义务（开源可满足）。

## 5. 已知局限与风险

1. **只对"绿幕 + 非绿色主体"的这类视频有效**；非绿幕/主体含绿会抠不掉或误抠。
2. **水印处理是硬切四角**，可能裁掉角色内容（已确认可接受）；水印在画面中部则清不掉。
3. **硬边缘抠像**：细发丝/半透明蕾丝/运动模糊处边缘偏硬、丢细节，达不到 AI matte 的柔和过渡。
4. **每段独立归一化 → 体形不一致**（由 §3 解决）。
5. **编码约束**：VP9-alpha-webm 是"事实标准中的非标准扩展"（BlockAdditional），通用播放器支持不一；
   alpha 帧与主色帧各一份 → bitrate 近似翻倍；4:2:0 色度子采样在透明边缘有损失。
6. **强耦合项目画布常量**（640×360 / PAD=30）：项目改画布则转换器目标需同步改。
   **（已决策：本阶段不强解耦，强制使用这些参数，作为当前约束；见《需求规格》§9 第 9 条）**。
7. **版本漂移**：嵌入的 ffmpeg/libvpx 版本会影响编码行为与结果一致性，需固定版本。
8. **素材合规**：AI 生成内容的使用/商用授权（上游 dsh-pet 明确素材禁止商用）。

## 6. 软件大方向（已定，细化随需求迭代）

把程序做成**单机自托管「桌宠运行时 + 素材工作台」**：既是常驻桌宠，也是本地**宠物/动作**的
制作与管理工具；浏览器控制台是统一管理面。

### 6.1 语义（与《需求规格》一致）

- 不用「素材集/素材」，统一**宠物（pet）+ 动作（action）**；动作只属于一只宠物。
- 转换作业的入口是「**给某只宠物加一个动作**」——上传绿幕 mp4 → 异步转换 → webm → 注册为该宠的动作。

### 6.2 转换作业形态（已决策）

- **异步任务 + 进度反馈**：解码/编码耗时，不阻塞控制台；控制台显示
  `queued / running / done / error` 与进度（如「转换中 3/12」），并给出失败报告。
- 程序级持有转换默认参数（画布 / 目标高 / 抠像 / CRF），单个作业可覆盖。

### 6.3 与行为状态机的关系

转换产物（webm）落入宠物的**动作池**；动作归类/归属见《行为状态机设计》。转换只管「mp4 → 能用 webm」，
归属管理属状态机一侧。

### 6.4 宠物全身照（远期 + 展示）

每只宠物可有**全身照**（`full_body_image`），作为**未来** AI 生成绿幕视频的**关键输入**
（全身照 + 动作提示词 → 出 mp4）；本阶段只在控制台展示，不做生成能力。

### 6.5 集成顺序

1. 先把「跨动画归一化批量化」做成工具级能力（`convert_assets <目录> --idle …`，见 §3）；
2. 内嵌 ffmpeg（libav\* 静态）接入，成为**异步转换作业**（见 §4）；
3. 把「上传 mp4 → 转换+归一化 → 注册为宠物动作」接入控制台素材工作台任务流。

> **进度**：第 3 步的「单 mp4 → 注册为宠物动作」**已接入控制台**（`POST /api/pets/{id}/import/video` +
> `GET /api/pets/{id}/jobs`，异步转换作业，进度见控制台），当前引擎用**系统 ffmpeg 二进制**；
> 第 2 步「内嵌 libav\*」仍待做（第 1 步「跨动画批量归一化」随「从视频新建宠物向导」一并后续实现）。

### 6.6 画布与打包（对应本轮决策）

- **画布**：不强解耦，转换与渲染均强制 640×360 / PAD=30（§5 第 6 条）——本阶段不改参数。
- **ZIP 传播包（决策）**：含 webm + 可选「动作→归属」`config`；**有 config → 导入时「预览/可编辑 → 确认导入」，
  无 config → 导入后用户自行配置**（详见《需求规格》/《行为状态机设计》§5、§6）。
